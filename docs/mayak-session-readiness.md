## Находка 1 — ✅ ИСПРАВЛЕНО (реальный баг, кросс-платформенный): гонка расхода токена

`src/lib/mayakSessionTokens.js` → `useMayakSessionToken()` делает read-modify-write
**без единой блокировки**:

```js
const store = await readStore();              // чтение ВНЕ лока
// ...
store.tokens[index] = { ...current, usedCount: current.usedCount + 1 };
await writeStore(store, [current.id]);        // запись (лок только на саму запись)
```

При одновременном входе N участников все читают `usedCount=0`, каждый пишет `1`,
последняя запись побеждает → **инкременты теряются**. В тесте 12 одновременных
входов дали `usedCount=1`. Это ровно сценарий «группа заходит по общему токену
в начале сессии».

Последствие: лимит входов по токену (`tokenUsageLimit`) под нагрузкой
**недосчитывается и фактически не соблюдается** (fail-open: люди входят, но счётчик
и «осталось попыток» врут). Регистрация участников этой проблемой **не затронута** —
`mutateSessionRuntime` держит чтение+запись под одним локом (в тесте все 12
параллельных регистраций и подсчёт участников корректны).

**Применённый фикс** (`src/lib/mayakSessionTokens.js`, `useMayakSessionToken`):
весь read-modify-write обёрнут в `withJsonFileLock(SESSION_TOKENS_FILE, …)`, стор
читается и пишется внутри одного лока (без вложенного `writeStore`, чтобы не
получить дедлок). Паттерн тот же, что в `mutateSessionRuntime`. После фикса
12 одновременных входов дают `usedCount=12` (стабильно). Схема:

```js
import { withJsonFileLock } from "@/lib/jsonFileLock";
export async function useMayakSessionToken(tokenValue) {
    return withJsonFileLock(SESSION_TOKENS_FILE, async () => {
        const store = await readStore();
        // ... все проверки и инкремент ...
        await writeStore(store, [current.id]);
        return { success: true, ... };
    });
}
```

(Аналогично стоит проверить другие read-modify-write в токенах/сессиях, где
чтение вне лока: `createMayakSessionToken`, `updateMayakSession` и т.п.)

## Находка 2 — ✅ ИСПРАВЛЕНО (робастность, специфично для Windows): EPERM при атомарной записи

`src/lib/jsonFileLock.js` → `writeJsonFileAtomic()` пишет через temp-файл и
`fs.rename(temp, target)`. На Windows `rename` поверх существующего файла изредка
даёт `EPERM` (файл открыт читателем/антивирусом/индексатором — читатели лок не
берут). В dev это всплывало как случайные 500/400 на `auto-approve`/`participant`.

- На Linux в проде `rename()` атомарен и так не падает — специфично для Windows.
- Хендлеры отдают такую ошибку как общий 400/500, что маскирует причину.

**Применённый фикс** (`src/lib/jsonFileLock.js`, `writeJsonFileAtomic`): ретрай
`fs.rename` на `EPERM`/`EEXIST`/`EBUSY`/`EACCES` (до 5 попыток с backoff), при
провале temp-файл убирается. На Linux эти коды в норме не возникают — поведение
не меняется.

**Остаётся на будущее** (не блокеры): для тяжёлой прод-нагрузки рассмотреть
перенос сессионного состояния в БД/Redis; читатели горячих файлов могли бы брать
лок при чтении.

> Примечание: в dev-режиме Next под параллельной нагрузкой отдельно всплывала
> внутренняя ошибка сервера `SyntaxError: Unexpected end of JSON input at loadManifest`
> — это артефакт `next dev` (манифесты дочитываются на лету). В проде
> (`next build` + `next start`) манифесты статичны, этого нет. Для финального
> гейта прогонять симуляцию против прод-сборки.

## Не реализовано: Telegram-уведомления на события сессии

В коде **нет** Telegram-пушей на события сессии (сдача/одобрение/отклонение/
блокировка). Ссылки в `CLAUDE.md` на `src/lib/telegramBot.js`,
`/api/mayak/telegram-webhook`, `/api/mayak/telegram-prepare`, `prep-session`
**устарели — этих файлов нет**. Env для бота задан, но к сессионному ревью не
подключён.

«Уведомления» в сессии сейчас — **внутриигровые**, через опрос `/state`:
очередь инспектора, блокирующее задание с таймером, статусы approve/reject у
участника, выдача тайной миссии. Всё это проверено и работает. Если нужны именно
Telegram-пуши — это отдельная фича (проектировать и реализовывать).

## Вердикт

- **Функциональный путь сессии — готов**: 18 человек, 3 стола, роли, кольцевое
  ревью, джокеры, дашборд отрабатывают корректно и подтверждены и headless
  (43/43), и визуально.
- **Обе находки по конкурентности — исправлены** (гонка `usedCount` + EPERM на
  Windows). Одновременный вход группы по общему токену теперь считается верно и
  не теряет записи. Симуляция стабильно зелёная на повторных прогонах.
- **Учесть при деплое**: отсутствие Telegram-пушей (если они ожидались
  продуктом) — это отдельная невыполненная фича, не блокер текущего пути.
- **Финальный гейт**: прогнать `scripts/mayak-session-sim.mjs` против прод-сборки
  (`next build && next start`) — тогда исчезнут dev-артефакты Next и результат
  станет чистым эталоном без ретраев в harness.
